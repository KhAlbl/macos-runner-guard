# Protected Controller Lifecycle Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implement pure host-collision verification and a transactional, root-protectable controller-generation lifecycle that always exposes either the fully verified old generation or the fully verified new generation.

**Architecture:** A redacted inventory is evaluated without mutation. Generation bytes are staged in immutable digest-named directories, recursively synced, and activated through one same-directory `ACTIVE.json` replacement plus parent-directory `fsync`. A transition journal makes interruption explicit; recovery never silently falls back. All tests use disposable fixtures, never a live runner root.

**Tech Stack:** Python 3.9+ standard library; descriptor-relative POSIX filesystem operations; canonical JSON; `/bin/bash` wrapper templates; unittest/pytest; macOS filesystem integration tests.

**Spec:** [Approved architecture §§5–6.4 and 9](../../ARCHITECTURE.md)

## Global Constraints

- Prerequisites: the contract/render/policy and cleanup-runtime plans are accepted on the same branch. This plan freezes small artifact-identity and operation-input-authority interchange schemas and tests them with canonical fixtures; it does not import or depend on child plan 4. Child plan 4 later converts a real verified archive/extraction report/finalization binding into those exact canonical bytes and an atomic context, and the umbrella integration gate must prove that adapter before any real operation package or adoption claim.
- Use generation manifest version `macos-runner-guard.generation.v1` and child-plan-1's accepted `runner_guard.bindings` canonical record serializer; do not create a second manifest encoding.
- Never target `/Library/Application Support/macos-runner-guard` in tests. Every writable target is beneath a new fail-if-exists temporary fixture.
- Never enumerate keychains or agents, read credential contents, or inspect another user's files. The bounded runner-root inventory may observe only the relative names and structural metadata permitted by the versioned live-state namespace policy; secret-bearing runner metadata such as `.runner` and `.credentials*` is never opened, hashed, or serialized. Local binding uses the exact service/root/account/runner-name identity and joins that unique name to the authenticated repository runner response; it never claims a locally discovered numeric runner ID.
- Never start, stop, register, remove, signal, or reconfigure a live service or runner.
- No automatic fallback is permitted when `ACTIVE.json` or its generation is invalid.
- Every transition is exact-instance and accepts no caller-supplied broad target.
- `.env` and `.path` are modeled and verified but remain untouched during ordinary generation updates.
- Proposal, filesystem/account readiness, official runner registration, structural controller installation, and post-job commissioning are distinct states; no helper may recreate a root owned by an earlier state or use post-job evidence to authorize the first job.
- Run every development and unit-test command as `PYTHONPATH="$PWD/src" .venv/bin/python`; shell state is never assumed across tasks. Use `/usr/bin/python3 -I -S` only for rendered standalone bootstrap subprocess tests and never to import the checkout.
- Each task ends in a focused commit; do not squash task commits while the subsystem is under review.

## Frozen Layout and Interfaces

```text
controller/
├── bootstrap/
│   ├── activate.py
│   ├── job-started.sh
│   └── job-completed.sh
├── generations/
│   └── <64-lowercase-hex-manifest-sha>/
│       ├── cleanup_controller.py
│       ├── instance.json
│       └── GENERATION_MANIFEST.json
├── TRANSITION/                    # optional live-generation journal transaction
│   └── record.json
└── ACTIVE.json
```

The separate initial-install journal lives at the instance parent as `.install-controller-transition/`; it is not a controller child and never aliases the generation journal at `controller/TRANSITION/record.json`.

`build_operation_request()` is the sole request constructor: it derives common repository/project/state/report fields from the validated contract and accepted envelope, accepts only the table's typed inputs for the selected literal, and returns a record that round-trips through the canonical serializer/loader. `write_operation_request()` uses absent-file mode `0444`, create-exclusive/sync/reread/digest verification. Every CLI operation spelling is exactly the underscore literal in the variant table. The common grammar is `scripts/build-operation-request.py --operation <exact_table_literal> --contract CONTRACT --verification-envelope ENVELOPE <exact-tag-flags> --output NEW_CONTEXT_DIRECTORY`; non-recovery tag flags are the kebab-case forms of exactly that table row's variant fields and no others. The CLI commits one hidden-directory transaction to the absent private mode-`0700` output: `operation-request.json` mode `0444`, plus `filesystem-preparation-plan.json` mode `0444` exactly when the selected request is in the preparation domain. For `prepare_filesystem`, it independently calls `build_filesystem_preparation_plan()` from the contract/envelope and uses that exact plan digest in the request; no caller supplies a plan or digest. Each `inspect_recovery` or `recover_*` tag accepts only `--recovery-report FILE --expected-recovery-report-sha256 DIGEST --previous-envelope FILE --blocked-authority-sha256 DIGEST`; the tag itself is the sole action selector, and the constructor derives every domain/state/nullable identity field, includes the exact canonical report-bound preparation plan when applicable, and requires the tag's uniquely mapped action to be present in the report's canonical `allowed_actions` tuple; a valid report may also carry the other state-permitted actions frozen by the recovery table, but those do not become selectors for this request. No `--action`, default action, alias, or second selector exists. It syncs/rereads both conditional members before the outer rename. An interrupted hidden context is abandon-only in version 1: it is never reused or removed by this toolkit, and the operator chooses a different fresh private parent/output for a later build; output or derived-hidden-name collision fails. No lifecycle or privileged operation refers to the abandoned private build path. The CLI performs no host mutation, accepts no target path/wrapper/command, and prints only operation/request SHA-256 plus the conditional plan SHA-256. `load_operation_request_bytes(data) -> OperationRequest` accepts only canonical JSON bytes for one row, requires the literal `operation` field, rejects unknown/missing/null-instead-of-absent fields, and enforces the domain/state/action mapping. Recovery report action `inspect_only` maps only to `inspect_recovery`; each mutating action maps one-to-one to its explicit `recover_*` tag above. Every recovery request is authorized only by `verify_recovery_binding()` and a state-`recovery` envelope, and its `blocked_operation_authority_sha256` must identify the exact still-present original operation quarantine whose execution resolution required host recovery. The origin/domain relationship is closed in both directions: `recovery_domain="prepare_filesystem"` requires `originating_operation="prepare_filesystem"` and `originating_host_state="proposal_ready"`; `recovery_domain="install_controller"` requires `originating_operation="install_controller"` and `originating_host_state="registered_pretransition"`; `recovery_domain="generation"` requires `originating_operation` in the exact set `{"upgrade_generation", "rollback_generation"}` and `originating_host_state="commissioned"`. Conversely, each of those four origins requires its stated domain and no other origin is accepted. The origin must match the digest-bound previous accepted envelope and blocked operation package. No cross-pair or other pair is valid. Operation-package staging recovery is a different `OperationRecoveryAuthority` path and never masquerades as host-transition recovery. There is no wildcard tag, caller action, default recovery action, or free path. Tests pin one complete canonical JSON byte fixture and CLI argv/context form for every row; interrupt every context boundary and prove a fresh-output retry without deleting the abandoned context; and mutate the discriminator, tag-specific flags, domain, blocked authority, both directions of the origin/domain mapping, state, nullable identity-field presence, plan/request pairing, output collision, and unknown keys. `canonical_artifact_identity_bytes(identity)`/`load_artifact_identity_bytes(data)` and `canonical_operation_input_authority_bytes(value)`/`load_operation_input_authority_bytes(data)` similarly freeze their exact schema versions/fields, strict member order/uniqueness, canonical bytes, and unknown-key rejection. Plan-3 unit tests use only canonical fixtures generated from these constructors; they are model evidence, not proof that a real ZIP supplied the values. `VerifiedOperationInput` has no fixture/public constructor and exists only after the context loader authenticates both externally supplied expected digests and live payload binding.
